# ALWAYS ON – Executive Summary & Technical Overview

## Executive Summary (Plain‑English)

Imagine a single desktop computer that keeps your entire drone‑based business running all the time.  The system automatically collects data from tiny, inexpensive drones, processes that data into maps and insights, handles customer orders through a friendly online forum, and even runs virtual pilots to fine‑tune how those drones fly.  All of this happens without you having to manually restart anything – the computer watches for new software updates, pulls fresh images, and keeps every component healthy.

The key points are:
- **One machine, one hub** – a Kubuntu 26 laptop with KDE Plasma manages everything from payments to simulations.
- **Drones on the field** – Raspberry Pi 5 boards equipped with LoRa radios collect data and talk back when they land.
- **Community & commerce** – A Mastodon server is your storefront and knowledge base; customers can ask questions, place orders, or customize their setup via a chat‑bot powered by a language model.
- **Automated analysis** – Images from the drones are automatically turned into maps, while simulations refine flight plans before you send a drone out.
- **Always on, low cost** – The whole stack runs in lightweight containers and only exposes the ports that really need to be public.

## Technical Stack Summary

### A. Platform & Runtime
- **Host OS:** Kubuntu 26 (Linux kernel 6.x), KDE Plasma 6.7 desktop environment.
- **Container Runtime:** Podman, rootless – no daemon, runs as a normal user.
- **Service Orchestration:** `systemd` units + timers for daily image refresh; optional Watchtower container for continuous monitoring.

### B. Core Services & Their Responsibilities
| Service | Role | Key Ports (Public) | Internal Dependencies |
|---------|------|---------------------|-----------------------|
| Corda | Payment ledger, receipt generation, private‑user list | 8888 RPC, 10000 Web UI (HTTPS via reverse proxy) | PostgreSQL (shared DB), Java runtime |
| MeshChatX | LoRaWAN gateway + WebSocket server for drones | 9000 WSS | LoRa radio driver on host, OpenClaw status endpoint |
| WebODM | Geospatial image processing pipeline | 8000 REST & WebUI (HTTPS) | Redis queue, PostgreSQL (optional), drone‑image folder |
| LM Studio | Language model inference server | 5000 FastAPI | GPU/CPU resources, Python runtime |
| OpenClaw | AI agent that posts to Mastodon | 8001 status (internal) | Calls LM Studio API, uses Mastodon REST API |
| Gazebo + ArduPilot + ROS + SB3 | Full vehicle & robot arm simulation | 11345 ROS Master, 5760 MAVLink UDP, 5000 SB3 API (internal) | ROS topics, ArduPilot telemetry, world files |

### C. Data Flow and Inter‑Service Communication
- **Drone → MeshChatX**: LoRaWAN packets are received by the host’s radio hat; MeshChatX forwards messages via WebSocket to OpenClaw.
- **OpenClaw ↔ LM Studio**: Text prompts and responses over HTTP (FastAPI).
- **Drone → Local Folder → WebODM**: Upon landing, drones push JPEG/RAW images to a shared directory; WebODM picks them up from the folder and processes them into orthomosaics.
- **Simulation Results**: Gazebo writes flight logs and arm trajectories to `/results`; these files are then available for analysis or export to external systems.

### D. Security & Exposure
- Only essential ports (8000, 8888, 9000, 11345, 5760) are mapped to the host; all other traffic stays within Podman’s internal network.
- TLS termination via Traefik/NGINX on the host; Mastodon interactions use HTTPS and OAuth tokens stored in `~/.config/mastodon`.
- Each pod runs as a dedicated non‑root user with read‑only mounts for code, ensuring least privilege.

### E. Why This Stack is Valuable
1. **Low‑Cost Autonomy** – A single desktop computer can orchestrate multiple drones and a complex vehicle simulation without expensive servers or cloud services.
2. **Full Data Loop** – From field data collection (LoRaWAN + Wi‑Fi imagery) to on‑device processing, AI inference, public communication, and simulation refinement—all automated.
3. **Scalability & Modularity** – Adding a new drone is as simple as attaching another LoRa radio hat; the same Podman pods can handle multiple vehicles because they communicate over the internal network.
4. **Cross‑Platform Compatibility** – The Raspberry Pi 5 units run KDE Plasma 6.7 (KALIOS) and are fully compatible with the host’s desktop environment, simplifying UI sharing or remote management.
5. **Regulatory & Compliance Ready** – Corda provides a tamper‑proof ledger; all data paths are logged by `systemd` and can be audited. The system can be extended to support GDPR/CCPA compliance via proper data retention policies.

### F. Future Enhancements
- **Automatic scaling of LM Studio workers** based on request load.
- **Container image signing** for secure updates.
- **Edge‑to‑cloud sync** for long‑term storage or analytics dashboards.
- **Integration with additional IoT protocols** (e.g., NB‑IoT, Sigfox) if required.

## 1. Installation Script (Run as root)

> **NOTE:** Execute this block *once* on your Kubuntu 26 machine to provision users, networks, systemd units and the daily update timer.

```bash
#!/usr/bin/env bash
set -euo pipefail

# ---------- 0️⃣ Environment ----------
sudo apt update && sudo apt upgrade -y
sudo apt install podman podman-docker systemd-user-container \
                redis-server postgresql lora-tools

# ---------- 1️⃣ Users & Network ----------
for svc in meshchatx webodm lmstudio openclaw mastodon_node ardupilot gazebo; do
    sudo adduser --disabled-password --gecos "" $svc
done

podman network create sim-net

mkdir -p /etc/pod_run_commands
chmod 700 /etc/pod_run_commands

# ---------- 2️⃣ PostgreSQL ----------
sudo -u postgres psql <<'EOSQL'
CREATE DATABASE app_shared;
CREATE USER app_user WITH PASSWORD 'StrongPass!';
GRANT ALL PRIVILEGES ON DATABASE app_shared TO app_user;
EOSQL

# ---------- 3️⃣ Helper Script ----------
cat > /usr/local/bin/run_pod.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
svc=$1
cmd=$(sed -n 1p "/etc/pod_run_commands/${svc}")
exec $cmd
EOF
chmod +x /usr/local/bin/run_pod.sh

# ---------- 4️⃣ Systemd Units ----------
cat > /etc/systemd/user/corda-node.service <<'EOF'
[Unit]
Description=Corda Node
After=network.target postgresql.service

[Service]
Type=simple
User=corda_node
ExecStart=/usr/local/bin/run_pod.sh corda-node
Restart=on-failure
StandardOutput=syslog
StandardError=syslog
SyslogIdentifier=corda-node

[Install]
WantedBy=default.target
EOF

# (Repeat similar blocks for meshchatx-server, webodm-web,
# lmstudio-headless, openclaw-agent, ros-master, gazebo-sim)
# ... omitted here for brevity – see full report below.

# ---------- 5️⃣ Daily Update Timer ----------
cat > /usr/local/bin/pod_update_all.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
for svc in $(ls /etc/pod_run_commands); do
    echo "Updating $svc"
    podman pull "$(sed -n 1p "/etc/pod_run_commands/${svc}")" 2>/dev/null || true
    systemctl --user stop "${svc}.service" 2>/dev/null || true
    systemctl --user start "${svc}.service"
done
EOF
chmod +x /usr/local/bin/pod_update_all.sh

cat > /etc/systemd/user/pod-update.timer <<'EOF'
[Unit]
Description=Daily Pod Image Update

[Timer]
OnCalendar=daily
Persistent=true

[Install]
WantedBy=timers.target
EOF

cat > /etc/systemd/user/pod-update.service <<'EOF'
[Unit]
Description=Run pod_update_all.sh

[Service]
Type=oneshot
ExecStart=/usr/local/bin/pod_update_all.sh
StandardOutput=syslog
StandardError=syslog
SyslogIdentifier=pod-update

[Install]
WantedBy=default.target
EOF

# ---------- 6️⃣ Enable Units ----------
systemctl --user daemon-reload
for svc in corda-node meshchatx-server webodm-web lmstudio-headless openclaw-agent ros-master gazebo-sim; do
    systemctl --user enable --now ${svc}.service
done
systemctl --user enable --now pod-update.timer

echo "Installation complete.  Reboot or log out/in to activate all units."

## 9 – Automation & Updates (cont.)
| Task | Detail |
|------|--------|
| **Daily Image Refresh** | Systemd timer `pod-update.timer` executes `/usr/local/bin/pod_update_all.sh`. The script pulls the latest image for each service, stops the old container, removes it, and restarts with the saved run command from `/etc/pod_run_commands/<service>`. This keeps all containers up to date without downtime.
| **Watchtower (Optional)** | Run `podman run -d --name watchtower \
    -v /var/run/docker.sock:/var/run/docker.sock \
    containrrr/watchtower --interval 3600` for real‑time monitoring of image updates. It will automatically pull new tags and restart containers when a newer version appears.

## 12 – Risk Assessment & Mitigation
| Risk | Impact | Likelihood | Mitigation |
|------|--------|------------|-------------|
| Container OOM (e.g., LM Studio GPU memory) | Service crash | Medium | Set `--memory` limits; monitor with `podman stats`; auto‑restart via systemd.
| LoRa packet loss | Incomplete telemetry | Low | Implement redundancy: store packets locally on Pi, resend if not acknowledged.
| Unauthorized access to Mastodon API | Data breach | Low | Store OAuth tokens in encrypted `.config/mastodon`, use HTTPS only, restrict IP ranges.
| Disk space exhaustion (image ingestion) | System halt | Medium | Auto‑rotate logs, set quota on `/home/scottw/drone_images` via `quota` or `edquota`.
| Dependency breakage (e.g., image pull failure) | Deployment freeze | Low | Pin image tags; maintain local registry mirror; include fallback script to retry pulls.

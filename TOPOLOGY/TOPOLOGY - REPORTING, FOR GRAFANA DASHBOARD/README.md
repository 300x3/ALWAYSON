# TOPOLOGY REPORTING — FOR GRAFANA DASHBOARD

This folder is the **reporting contract** for the ALWAYS ON one-page topology. It
records the structure of the graphic and the data behind it, so the Grafana
dashboard can be built and maintained against a stable schema instead of being
re-derived from the SVG each time.

The graphic lives at `../SINGLE GRAPHIC/` and is generated by
`../SINGLE GRAPHIC/build_svg.py`. **That file is the source of truth for the
model.** Nothing in this folder duplicates it by hand — the JSON here is
exported from it by `export_topology_model.py`, so the two cannot drift.

## Files

| File | Purpose |
|---|---|
| `README.md` | This document — the format and how to maintain it |
| `topology-model.json` | Exported model: bands, sections, nodes, edges |
| `export_topology_model.py` | Regenerates the JSON from `build_svg.py` |
| `grafana-mapping.md` | How each model field maps to Grafana panel concepts |

## The model in one paragraph

The system is drawn as **9 numbered bands** read left to right, each a vertical
box. Bands 1–5 are one box each and all share a common top edge. Bands 6, 7 and 8
(sales, simulation, secrets) are **stacked in a single column** — three separate
boxes, each with its own number and border. Band 9 is the single last box. Inside
a band, cards are grouped into **named sections**; a section is just a titled run
of cards.

The single organising rule, stated in the graphic itself: **the doors are the
outside world → the stores, the adapters → the domains, the stores → sales, the
rehearsed worlds and the wallet kept apart → what actually happens.**

## Fields that matter for reporting

Each node carries these. Only the first five are load-bearing for a dashboard.

| Field | Type | Notes |
|---|---|---|
| `id` | string | Stable key. **Never renumber or reuse** — panel history depends on it |
| `band` | string | One of the 9 band keys; sets the node's column |
| `title` | string | The name, already title-cased for display |
| `purpose` | string | One line: what it is for |
| `status` | enum | `IMPLEMENTED` · `IN PROGRESS` · `PLANNED` · `BLOCKED` · `PARTIAL` |
| `details` | string[] | Supporting lines — versions, ports, scope |
| `cls` | enum | Semantic class: `ext`, `adp`, `work`, `ledger`, `data`, `hw`, `rf`, `host`, `sec` |
| `sec` | string | Authority references into README v6 (§-numbers, `ES.1`, `6.A.2` …) |

Edges are `(source_id, target_id, label, kind)`, where `kind` is the visual
weight: `ok` (green solid — approved, mTLS, signed, audited), `normal` (grey
dashed — ordinary internal), `rf` (amber heavy — radio, no IP), `no` (red dotted
— prohibited by v6 §4.3).

## Regenerating

```sh
cd "/ALWAYSON/TOPOLOGY/TOPOLOGY - REPORTING, FOR GRAFANA DASHBOARD"
python3 export_topology_model.py          # rewrites topology-model.json
cd "../TOPOLOGY - SINGLE GRAPHIC" && python3 build_svg.py   # rewrites the SVG/PDF
```

Run the exporter **after** any edit to `build_svg.py`, and commit both together.

## Maintenance rules

1. **Adding a component**: add the node in `build_svg.py` with a unique `id`, its
   `band`, and a `status`. The builder validates that every node sits in exactly
   one section and that its section's band matches. Then re-run the exporter.
2. **Never renumber `id`s.** Add and retire instead. Grafana panel state, saved
   queries and any recorded history key off them.
3. **Status is a plan statement, not telemetry.** If the dashboard needs live
   state, it comes from the live inventory (`../topology-inventory.json`), not from
   this model.
4. **Keep `sec` populated.** It is what lets a panel link back to the authority
   document, and it is the fastest way to answer "why does this exist?".

## Known gaps

- The exporter currently emits only fields the builder already holds. There is no
  `first_added` / `last_changed` date per node, so the dashboard cannot yet show
  "changed this week" without diffing `topology-model.json` across commits.
- `notes` (the `BLOCKED` reason strings) are exported but not yet surfaced in the
  existing dashboard JSON.
